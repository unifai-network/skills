# PRD Writer

将模糊的产品想法变成工程团队可以直接开发的产品需求文档。

## 核心工作流

整个流程分三个阶段：**澄清 → 生成 → 完善**。不要跳过澄清阶段——一份好的 PRD 取决于你对需求的理解深度。

### 阶段一：澄清需求

拿到用户输入后，先快速判断信息完整度。以下维度是你需要明确的：

1. **用户场景**：谁在用？什么场景下触发？解决什么问题？
2. **核心流程**：用户从哪里进入，经过哪些步骤，最终达成什么结果？
3. **页面范围**：涉及哪些页面或模块？是新页面还是在现有页面上改？
4. **数据来源**：展示的数据从哪来？需要新接口还是复用现有接口？
5. **边界情况**：空状态、错误状态、权限差异、极端数据怎么处理？

**提问策略：**

- 一次最多问 3-5 个问题，按优先级排列，不要一次性抛出所有问题把用户淹没
- 对于你能合理推断的部分，给出你的假设并请用户确认，而不是留空等答案
- 把问题按"必须确认"和"我先这么假设，你看看对不对"分类呈现
- 如果用户说"你先写，我来改"，那就基于合理假设先生成完整 PRD，在不确定的地方标注 `[待确认]`

**示例对话：**

用户说："加一个排行榜功能"

你的回应结构：
```
我先确认几个关键点：

必须确认：
1. 排行榜的排序指标是什么？（比如 ROI、交易量、收益额）
2. 排行榜是所有用户可见还是需要主动加入？

我先按以下假设来写，不对的话你告诉我：
- 排行榜入口放在左侧导航栏
- 默认展示前 50 名 + 用户自己的排名
- 按 ROI 降序排列，ROI 相同时按 PnL 排序
```

### 阶段二：生成 PRD

确认关键信息后（或用户要求你直接写），按以下结构生成文档。

## PRD 文档结构

```
# [功能名称] 产品需求文档

## 1. 概述
  - 背景与目标
  - 核心用户场景

## 2. 前端需求
  - 2.1 [页面/模块名称]
    - 页面原型图（ASCII）
    - 交互说明
  - 2.2 [页面/模块名称]
    - ...
  （按页面或模块拆分，每个都有原型图 + 交互说明）

## 3. 后端需求
  - 3.1 数据字段定义
  - 3.2 业务规则与逻辑
  - 3.3 接口设计概要
  - 3.4 边界情况与异常处理

## 4. 待确认事项（如有）
```

## 前端需求写作指南

前端需求的目标是让工程师和设计师不用猜就能知道"页面长什么样"和"用户操作后会发生什么"。

### ASCII 原型图

每个关键页面状态都要给出 ASCII 原型图。原型图不是装饰，而是用来消除理解歧义的。

**原型图规范：**

- 用 `+--+` `|  |` 画框，用 `-` 画分隔线
- 用 `[ 按钮文案 ]` 表示按钮
- 用 `(○)` 表示未选中的 radio，`(●)` 表示选中
- 用 `[ ]` 表示未选中的 checkbox，`[✓]` 表示选中
- 用 `▼` 表示下拉菜单可展开
- 用 `>` 表示可点击跳转
- 用 `...` 表示内容可以被截断或省略
- 用 `<输入框提示文字>` 表示输入框
- 用 `───` 做水平分隔
- 标注关键尺寸和间距只在有设计要求时需要

**示例——排行榜页面：**

```
+----------------------------------------------------------+
| ☰  Logo    Dashboard   Portfolio   Leaderboard           |
+----------------------------------------------------------+
|                                                          |
|  🏆 Leaderboard                    [ Join Leaderboard ]  |
|                                                          |
|  +------------------------------------------------------+|
|  | Rank | User        | Portfolio | PnL      | ROI      ||
|  |------|-------------|-----------|----------|----------||
|  | 1    | @alice 🖼   | $12,340   | +$2,340  | +23.4%   ||
|  | 2    | @bob 🖼     | $8,120    | +$1,820  | +18.2%   ||
|  | 3    | User_c      | $6,500    | +$1,200  | +15.1%   ||
|  | ...  | ...         | ...       | ...      | ...      ||
|  | 50   | @dave 🖼    | $1,200    | +$80     | +2.1%    ||
|  |------|-------------|-----------|----------|----------||
|  | 1232 | You ⭐      | $3,400    | +$540    | +8.2%    ||
|  +------------------------------------------------------+|
|                                                          |
+----------------------------------------------------------+
```

**需要画原型的时机：**

- 新页面或新模块的默认状态
- 关键交互后的状态变化（展开/收起、选中/取消、悬浮提示）
- 空状态、错误状态、加载状态（如有必要）
- 不同用户角色看到的差异视图（如有）

### 交互说明写作规范

交互说明是前端需求的核心。每一条都要回答"用户做了什么"→"页面怎么响应"。

**写作原则：**

1. **以用户操作为起点**：每条描述以用户动作开头——"点击"、"悬浮"、"滑动"、"输入"、"选中"
2. **明确状态变化**：说清楚操作前后的组件状态对比
3. **写出具体文案**：按钮上写什么字、提示框显示什么内容、空状态展示什么文案——都要写出来，不要留给开发猜
4. **覆盖互斥和联动逻辑**：当组件之间有联动关系（比如全选和单选的互斥），要完整描述逻辑链

**交互说明模板：**

```
[操作] → [响应] → [结果状态]
```

**示例写法（按实际场景来写，以下是不同类型的参考）：**

**筛选器交互：**
- 点击 "Filters" 按钮展开下拉菜单，默认选中 "All"
- 当 "All" 处于选中状态时，点击其他选项（如 "Drift"）："All" 变为未选中，"Drift" 变为选中
- 当已有单项选中（如 "Drift"）时，点击另一项（如 "Meteora"）：两项同时选中（多选模式）
- 当取消所有单项选中时，自动回到 "All" 选中状态
- 选中项变化后，列表数据实时过滤刷新，无需手动确认

**操作按钮交互：**
- Action 列包含三个图标按钮，鼠标悬浮时分别显示 tooltip：
  - 第一个图标：悬浮显示 "Deposit"
  - 第二个图标：悬浮显示 "Withdraw"
  - 第三个图标：悬浮显示 "Export Private Key"
- 点击 "Withdraw" 弹出提现弹窗，包含金额输入框和确认按钮

**数据展示切换：**
- 页面顶部增加 "USD / Native" 切换开关，默认选中 "USD"
- 切换为 "Native" 时，Value 列显示币本位金额（如 SOL、ETH），保留 4 位小数
- 切换不影响排序逻辑，仅改变显示单位

**要避免的模糊写法：**

| 模糊写法 ❌ | 具体写法 ✅ |
|---|---|
| "用户可以筛选" | "点击 Filters 展开下拉菜单，支持多选，选中后列表实时刷新" |
| "显示提示信息" | "悬浮时显示 tooltip，文案为 'Deposit'" |
| "展示用户信息" | "字段包括：username（昵称）、X 头像（如已绑定）、portfolio 美元价值" |
| "需要一个弹窗" | "点击 Withdraw 后弹出弹窗，包含金额输入框（placeholder: 'Enter amount'）、最大可提现金额显示、[Confirm] 和 [Cancel] 按钮" |

## 后端需求写作指南

后端需求的目标是让后端工程师明确知道"存什么数据"、"怎么算"、"怎么返回"、"边界怎么处理"。

### 数据字段定义

每个关键字段都要包含：

```
字段名：
  - 定义：这个字段代表什么含义
  - 数据类型：string / number / boolean / timestamp / ...
  - 计算方式：（如果是计算字段）具体计算公式或逻辑
  - 数据来源：从哪个表或接口获取
  - 更新频率：实时 / 定时（多久一次）
  - 测试验证方式：（如果适用）如何验证这个数据是对的
```

**示例：**

```
PnL（盈亏金额）：
  - 定义：用户钱包在指定时间范围内通过交易产生的累计盈亏美元价值
  - 数据类型：number（美元，保留 2 位小数）
  - 计算方式：仅计算交易产生的盈亏，不包括存款和取款
  - 计算窗口：支持 1D / 7D / 30D / ALL 四个维度
  - 测试验证：将单个钱包地址放入 LP Agent 查看对应时间段的 total profit，
              结果差异应在合理范围内（主要差异来自 SOL 价格波动）
```

### 业务规则与逻辑

用清晰的条件-动作格式描述业务规则：

```
规则：[规则名称]
  - 条件：当 [什么情况发生] 时
  - 动作：执行 [什么操作]
  - 约束：[额外限制条件]
  - 与其他规则的关系：[是否可叠加/互斥]
```

**示例：**

```
规则：策略 Creator 奖励
  - 条件：有用户跟单使用该策略进行交易时
  - 动作：策略 Creator 获得跟单钱包每笔交易费的 20% 作为奖励
  - 计入范围：当前正在跟单该策略的所有钱包的每笔策略交易
  - 与邀请返佣的关系：可叠加。通过 Creator 邀请链接注册的用户使用该策略后，
    Creator 可获得最高 10% 邀请返佣 + 20% 跟单奖励
  - 结算周期：按天或按周结算（需确认）
  - 提现：与邀请返佣共用提现入口，支持 claim USDC/SOL
```

### 接口设计概要

不需要写完整的 API 文档，但要说清楚关键接口的输入输出：

```
接口：获取排行榜数据
  - 请求参数：page_size（默认 50）、user_id（当前用户）
  - 返回内容：
    - 排行榜前 N 名列表（含 rank、username、avatar、portfolio、pnl、roi）
    - 当前用户的排名和数据（即使不在前 N 名内也要返回）
  - 排序规则：ROI 降序，ROI 相同时 PnL 降序
  - 缓存策略：[按需填写]
```

### 边界情况与异常处理

这一节容易被忽略但对开发质量影响很大。用表格或列表形式列出：

```
| 场景 | 处理方式 |
|------|---------|
| ROI 计算时本金为 0 | 返回 0% 或 N/A，避免除零错误 |
| 用户 join 后删除了上榜策略 | 从排行榜移除该用户 |
| 用户解绑了 X 账号 | 排行榜同步清空该用户的 X 头像和 Handle |
| 同一 X 账号被多个 uid 尝试绑定 | 仅允许一个 uid 绑定，需先解绑才能被其他 uid 使用 |
| 数据加载失败 | 显示重试按钮，文案："加载失败，请重试" |
| 列表为空 | 显示空状态插图和引导文案 |
```

## 阶段三：完善与迭代

生成初版 PRD 后，引导用户审阅和反馈：

- 主动提示用户关注可能遗漏的边界情况
- 如果某个模块的需求还比较粗，主动提出并建议细化
- 对标注了 `[待确认]` 的部分逐一确认

## 输出格式

PRD 默认输出为 Markdown 格式。如果用户要求，可以转为 Word 文档（.docx）。

文档语言跟随用户的输入语言：用户用中文提需求就输出中文 PRD，用英文就输出英文。

## 输出长度指引

根据需求复杂度调整文档详细程度：

- **小功能**（单个组件变更、加一个按钮）：聚焦变更点，1-2 页足够
- **中等功能**（新模块、新页面）：完整覆盖所有章节，3-6 页
- **大功能**（多页面联动、含复杂后端逻辑）：拆分模块详细展开，可以更长

不要为了凑篇幅写废话，也不要为了简短而省略关键信息。
